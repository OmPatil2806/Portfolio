Multi-Store Management System

One owner login, three stores, no more notebooks.

  • 2 roles
  • 3 stores
  • Salaries hidden at API level
View on GitHub

Problem

An owner running a grocery, a clothing and an electronics store was tracking stock, sales and payroll across three sets of notebooks. This replaces them with one application that runs locally on the store network.

Data

Tenancy
3 stores — grocery, clothing, electronics — under one owner login.
Roles
2 — owner and employee, with separate logins.
Deployment
Runs locally on the store network.

Approach

  • Per-store inventory with owner-only price control and low-stock flags.
  • Cart checkout taking cash, card, UPI or other, with an atomic stock decrement.
  • Employee codes such as GRO-0004; deactivating an employee invalidates their tokens.
  • Dashboards for revenue, top products, stock value and payment mix, built with Recharts.
  • One-click formatted .xlsx export, per store or across all stores.

Results

Security design

Identity and store are derived from the JWT, and a client-sent store_id is ignored outright. Salary is removed in the response schema, not merely hidden in the UI — an employee calling the API directly still cannot read it.

This project is a working application rather than a measured experiment, so there is no benchmark comparison to show here. The numbers that describe it are in the data section above.

Limitations
& honest notes

  • Built for a single owner with three stores; it is not a general multi-tenant SaaS.
  • Runs locally on the store network, so there is no hosted deployment or live demo.
  • SQLite is sufficient at this scale and would need replacing for concurrent multi-site use.
